# /ship-feature <機能名>

**引数:** 機能名 (例: `/ship-feature F11`)

---

## ステップ0: 前提確認

`.steering/` 配下から引数の機能名に対応する `tasklist.md` を読み込む。
未完了タスク（`[ ]`）が残っている場合は `/implement-feature <機能名>` を先に完了させるよう案内して終了する。

---

## ステップ1: 実装検証（サブエージェント）

`implementation-validator-java` サブエージェントを起動して品質を検証する。

- `subagent_type`: "implementation-validator-java"
- `prompt`: "今回実装した `[機能名]` に関する全ての変更点の品質を検証してください。コーディング規約・エラーハンドリング・テスト可能性・既存パターンとの整合性を重点的に確認してください。"

サブエージェントの指摘を受けた場合は修正してから次に進む。

---

## ステップ2: 自動テスト

以下を順番に実行し、全てパスすることを確認する。失敗した場合は原因を分析・修正してから再実行する。

```bash
./gradlew checkstyleMain checkstyleTest
./gradlew spotbugsMain
./gradlew test
./gradlew build -x test
```

---

## ステップ3: 振り返り

`tasklist.md` の末尾に「実装後の振り返り」セクションを追記する。

```markdown
## 実装後の振り返り

**実装完了日**: YYYY-MM-DD

### 計画と実績の差分
| 項目 | 計画 | 実績 |

### 設計判断の記録
> 「なぜそうしたか」が消えやすい意思決定を残す。複数の選択肢があった場合や、仕様書に書かれていない理由で実装方針を決めた場合に記録する。

- **[判断した内容]**: [選んだ理由・却下した選択肢]

### 発生した不具合と対処
> 実装・テスト中に遭遇したエラー・想定外の挙動と、その原因・解決策を残す。次の機能で同じミスをしないための記録。

- **[エラー/不具合の内容]**: [原因と解決策]

### 技術的な学び

### 次回への改善提案
```

---

## ステップ4: PR 作成

feature ブランチから develop への PR を作成する。

- タイトル: `feat(<機能名>): <実装内容の概要>`
- ボディ: 実装した機能・変更ファイル・テスト確認済みの旨を記載する
